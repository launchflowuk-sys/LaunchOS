```
provisionWordPressWebsite(domain, siteTitle, adminEmail, adminUser, adminPassword, language)
```

1. Does the domain already exist? 2. If not, create it. 3. Read back username,
docroot, order id. 4. Is WordPress already installed? 5. If not, install it.
6. Poll until done or failed. 7. Never install twice. 8. Return site URL, admin
URL, status, failure reason. 9. Idempotent, never overwrite without an explicit
flag.

### The one thing that is blocked, and what to do about it

Step 5 cannot be built yet:

```
POST /api/hosting/v1/wordpress/installations
  → 405. Supported methods: GET, HEAD.
```

Reading installations works. Installing does not, on this token, on v1, and
`hosting/v2` does not exist. Hostinger's own CLI documents an install command,
so it reaches something this token cannot — a scope, a tier, or an unexposed
surface.

**Shoji is asking Hostinger.** Do not wait for the answer and do not keep
probing at it. Build everything around it now:

- `HostingProvisioner` interface + mock, rule 4, in `packages/integrations`.
- Hostinger implementation for create / delete / list — all verified working.
- `installWordPress` as a method on the interface, implemented in the mock, and
  in the Hostinger adapter throwing a named "not enabled on this token" error
  until the 405 becomes a 200. Then it is a one-function change.
- Both writes are **asynchronous** — `{"message":"Request accepted"}`, the site
  appears ~10s later. Poll the list; never treat 200 as done. A build that never
  appears must fail loudly, not proceed into a docroot that is not there.
- **Write teardown at the same time as creation.** Not after. A pipeline that
  creates sites and leaks them fills a 75GB disk that has already hit 84% twice
  in two days.

### The design decision to keep

Deploy to a review URL, **team checks, Shoji approves, then the client hears.**
Nothing reaches a client's real domain or inbox before he has said yes. A
generated site landing live unreviewed cannot be walked back — the client has
seen it and so has Google.

And note: for the review stage the generated site is HTML and CSS. It does not
need WordPress to be looked at. SFTP to the docroot is enough, which is why the
405 does not block the chain — only the last step of it.

## Things that will bite

- **`.gitignore` had an unanchored `coverage/`** and silently swallowed an app
  route. It is anchored now, but the lesson stands: if a screen 404s in
  production and renders locally, check `git ls-files` before anything else. A
  307 to `/sign-in` proves nothing — every path under an authed route answers
  that, real or not.
- **A `"use client"` file must not *value*-import `@launchos/core`.** It drags
  the database driver into the browser bundle and dies with `Can't resolve
  'net'`, while typechecking perfectly. Types only, with `satisfies` to stop the
  restated constants drifting. This cost two rounds today.
- **`heartbeat.test.ts` is flaky** — it asserts across every active organisation
  and collides with organisations other tests create in parallel. Passes 3/3
  alone. Not yet fixed.
- **Deploys fill the disk.** Six pushes took it from 22% to 84%. Batch them, and
  run `/usr/local/bin/docker-reclaim` after — it prunes images and build cache,
  never volumes. Check for stopped containers first; all 13 were running, so no
  other app's image was at risk.
- **A push takes ~4 minutes** to reach production. Tell him when something has
  actually landed, not when it was pushed — the image tag on the container is
  the truth.
- **The wizard is `launchflow.co.uk/start`, not `os.`** The admin domain will
  always 404 it.
