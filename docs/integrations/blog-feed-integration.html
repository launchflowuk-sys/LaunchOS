Integration Specification

Blog feed integration

LaunchOS writes, schedules and approves each client's blog posts, then serves them over one public endpoint. Every client application renders its own blog by reading that endpoint. This is what each application has to add.

LaunchFlow UK Limited 15 September 2026 For the developer or agent doing the work

01

What this is, and why it is a pull

A client's month of content is planned, written by the Content Writer, approved by Shoji and scheduled inside LaunchOS. When a post reaches its scheduled minute, LaunchOS marks it published. Nothing is sent anywhere.

The application then fetches its own published posts and renders them as its own pages, on its own domain. LaunchOS is the source of truth; the application is the shop window.

Why not have LaunchOS push into each application?

Because that would mean a write endpoint, a shared secret and a stored schema in every one of roughly fifteen applications — and any later change to the contract would mean redeploying all of them. A pull is one endpoint, no credentials anywhere, and a contract that can be extended without touching a single client app.

Precedent

This is the same shape as the existing /api/public/reviews endpoint, which already serves clients' Google reviews to their own sites for exactly this reason: a client's website should not have to hold a credential to display its own content.

WordPress sites are the exception and need none of this. LaunchOS writes posts directly into WordPress over its REST API, as it always has. This document is only for the applications — Next.js on Coolify, static sites, anything custom.

02

The endpoint

No authentication. No API key. No headers required. CORS is open, so server or browser both work.

List a site's posts

GET https://os.launchflow.co.uk/api/public/blog?site=<site-slug>

Fetch one post

GET https://os.launchflow.co.uk/api/public/blog?site=<site-slug>&post=<post-slug>
ParameterRequiredMeaning
siteYesThe website's slug in LaunchOS. Shoji will give you this per application; it is fixed and will not change.
postNoA single post's slug, taken from the slug field of a listing entry. Omit it to get the list.

FieldTypeNotes
idstringStable for the life of the post. Use as a React key.
slugstringThe permanent address. Use it as your route segment. It is settled when the post is published and never changes, even if the title is later edited.
titlestringNever empty; falls back to "Untitled".
htmlstringAlready sanitised HTML. Headings, paragraphs, lists, links. Render it directly — see section 4.
urlstringThe canonical URL on the client's own domain. Use for rel="canonical", sitemaps and share links.
imageUrlstring · nullFeatured image. Often null — the layout must look right without one.
publishedAtstringISO 8601, UTC. Format for display in the app.

Status codes

CodeBodyWhat the application should do
200{ ok: true, data }Render. An empty posts array is a valid answer — show an empty state, not an error.
400{ ok: false }site was missing. A bug in the integration, not a runtime condition.
404{ ok: false }Hide the blog, or return your own 404 for a single post. Never surface an error page.
429{ ok: false } + retry-afterServe the last good copy. 120 requests per minute per IP; you should never see this if you cache.
One 404 for every reason

An unknown site, a blog switched off, a deleted site and an unknown post all return the same 404 on purpose — anything else would tell the internet which slugs exist. Treat 404 as "there is no blog here" and move on.

Caching

Responses carry cache-control: public, max-age=300 and stale-while-revalidate=300. Five minutes, not an hour, because a post publishes at a scheduled minute and a long cache would make that schedule a lie.

At most 50 posts are returned per request, newest first. There is no pagination.

03

What every application must build

Two routes, one fetch helper. That is the whole job.

  • /blog — the index. Title, date, excerpt or image, linking to each post.
  • /blog/[slug] — one post. Title, date, image if present, then the html.
  • A 404 from /blog/[slug] when the slug is unknown. Do not redirect to the index.
  • Revalidation so a newly published post appears within minutes without a redeploy.
  • rel="canonical" pointing at the url field.
  • Posts in the sitemap, so they get indexed.
  • A link to /blog from the site's own navigation or footer. A blog nothing links to is a blog nobody reads.
Do not

Do not copy posts into the application's own database. Do not build a write endpoint for LaunchOS to call. Do not add an API key. Do not cache for longer than five minutes. Do not re-render the html through a markdown parser — it is already HTML.

04

Reference implementation — Next.js App Router

Written for the Next.js applications, which is most of the estate. Adapt freely; the contract is the endpoint, not this code.

lib/blog.ts 
const BASE = "https://os.launchflow.co.uk/api/public/blog";

/** This application's site slug in LaunchOS. Shoji supplies it. */
const SITE = process.env.NEXT_PUBLIC_LAUNCHOS_SITE_SLUG ?? "";

export type BlogPost = {
  id: string;
  slug: string;
  title: string;
  html: string;
  url: string;
  imageUrl: string | null;
  publishedAt: string;
};

/**
 * Five minutes matches the endpoint's own cache header, so a scheduled post
 * appears within minutes of publishing without a redeploy.
 */
const REVALIDATE = 300;

async function read<T>(query: string): Promise<T | null> {
  if (!SITE) return null;
  try {
    const response = await fetch(`${BASE}?site=${encodeURIComponent(SITE)}${query}`, {
      next: { revalidate: REVALIDATE },
    });
    // 404 is "no blog here", not a fault. Anything else non-OK is transient.
    if (!response.ok) return null;
    const payload = await response.json();
    return payload?.ok ? (payload.data as T) : null;
  } catch {
    // Never let the blog take the page down with it.
    return null;
  }
}

export async function listPosts(): Promise<BlogPost[]> {
  const data = await read<{ site: string; posts: BlogPost[] }>("");
  return data?.posts ?? [];
}

export async function getPost(slug: string): Promise<BlogPost | null> {
  const data = await read<{ site: string; post: BlogPost }>(`&post=${encodeURIComponent(slug)}`);
  return data?.post ?? null;
}

import Link from "next/link";
import { listPosts } from "@/lib/blog";

export const revalidate = 300;

export const metadata = { title: "News & advice" };

export default async function BlogIndex() {
  const posts = await listPosts();

  if (posts.length === 0) {
    return (
      <main>
        <h1>News &amp; advice</h1>
        <p>Nothing published yet — check back soon.</p>
      </main>
    );
  }

  return (
    <main>
      <h1>News &amp; advice</h1>
      <ul>
        {posts.map((post) => (

            <Link href={`/blog/${post.slug}`}>{post.title}</Link>
            <time dateTime={post.publishedAt}>
              {new Date(post.publishedAt).toLocaleDateString("en-GB", {
                day: "numeric", month: "long", year: "numeric",
              })}
            </time>
          </li>
        ))}
      </ul>
    </main>
  );
}
app/blog/[slug]/page.tsx 
import { notFound } from "next/navigation";
import { getPost, listPosts } from "@/lib/blog";

export const revalidate = 300;

/** Pre-render what exists at build time; anything newer renders on demand. */
export async function generateStaticParams() {
  const posts = await listPosts();
  return posts.map((post) => ({ slug: post.slug }));
}

export async function generateMetadata({ params }: { params: Promise<{ slug: string }> }) {
  const post = await getPost((await params).slug);
  if (!post) return {};
  return {
    title: post.title,
    // The canonical is the client's own domain, which is where `url` points.
    alternates: { canonical: post.url },
    openGraph: {
      title: post.title,
      type: "article",
      publishedTime: post.publishedAt,
      ...(post.imageUrl ? { images: [post.imageUrl] } : {}),
    },
  };
}

export default async function BlogPost({ params }: { params: Promise<{ slug: string }> }) {
  const post = await getPost((await params).slug);
  if (!post) notFound();

  return (
    <article>
      <h1>{post.title}</h1>
      <time dateTime={post.publishedAt}>
        {new Date(post.publishedAt).toLocaleDateString("en-GB", {
          day: "numeric", month: "long", year: "numeric",
        })}
      </time>
      {post.imageUrl ? <img src={post.imageUrl} alt="" /> : null}
      {/* Already sanitised by LaunchOS — see section 5 before changing this. */}
      <div dangerouslySetInnerHTML={{ __html: post.html }} />
    </article>
  );
}
app/sitemap.ts — add the posts 
import { listPosts } from "@/lib/blog";

export default async function sitemap() {
  const posts = await listPosts();
  return [
    { url: "https://example.co.uk/blog", changeFrequency: "weekly" as const },
    ...posts.map((post) => ({ url: post.url, lastModified: post.publishedAt })),

}
One environment variable

NEXT_PUBLIC_LAUNCHOS_SITE_SLUG in Coolify, per application. Nothing secret, so the NEXT_PUBLIC_ prefix is fine — but nothing in the code above needs it on the client either, so a plain LAUNCHOS_SITE_SLUG works just as well and is tidier.

05

The one thing to be careful about

The code above uses dangerouslySetInnerHTML. That is deliberate and it is safe in this specific case, for reasons worth stating so nobody has to guess:

  • The HTML is produced by LaunchOS from Markdown through markdownToSafeHtml, which emits a fixed, small set of tags and no attributes that can execute.
  • The Markdown is written by the Content Writer and approved by a human before it can ever be published. It is not user-submitted content.
  • The endpoint only ever serves published items, so nothing unapproved is reachable.
If you would rather not

Run it through DOMPurify (or sanitize-html server-side) on the way in. Belt and braces costs nothing and no one will argue with you. What you must not do is feed it to a Markdown renderer — it is already HTML and you will get escaped tags on the page.

07

Shoji's side — what has to be true in LaunchOS

Not the developer's job, but here so you know who to chase when the endpoint 404s.

  • The website record has a slug. It is nullable, and a blog cannot be served without one — LaunchOS refuses to publish rather than create an unreachable post.
  • A Blog channel is connected on the client's Content tab, pointing at that website, and switched on.
  • The client's Blog service is switched on under their Services tab. The switch decides whether posting happens — not the subscription tier.
  • The month has been planned and the posts drafted and approved. Nothing publishes without Shoji approving it.
08

Questions worth a second opinion

These are the calls already made. If the reviewing agent or developer disagrees with any of them, this is where to say so — an answer of "this is fine" is a useful answer too.

  1. Pull over push. Is serving posts from LaunchOS right, versus giving each of ~15 applications a write endpoint and a shared secret? The trade was made on operational cost: one contract, no distributed credentials, no fan-out redeploy to change anything.
  2. HTML over Markdown on the wire. Sanitised HTML means no application needs its own Markdown renderer, at the cost of dangerouslySetInnerHTML. Would you rather ship Markdown and let each app render it?
  3. Five minutes of cache. Long enough to protect the origin, short enough that a scheduled publish is honest. Too short? Too long?
  4. Unauthenticated. The content is public by definition — it is a blog. Is an open, rate-limited, CORS-open read endpoint acceptable, or would you want a key despite the per-application cost of managing one?
  5. 50 posts, no pagination. Fine for monthly posting for years. Worth adding a cursor now, or when it is actually needed?
  6. Slug shape. title-slug plus eight hex characters of the post id, so two posts sharing a title cannot collide and the address survives a retitle. Uglier than a bare title slug. Right trade for SEO?
